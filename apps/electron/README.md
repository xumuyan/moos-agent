# Moos Electron 本机开发版

以 Moos 的 Electron 主进程打开 DSH 的原版工作台。macOS 构建阶段从 DeepSeek Harness Desktop 0.2.2-rc.1 取得 Electron 44.7.0 和工作台 Host，组装为内置 PI、Host 与插件安装器的 Moos 应用包。

```sh
npm run build:app
```

构建优先读取 `~/Library/Application Support/dev.moos.agent.build-sources/DeepSeek Harness.app`，也可从 `/Applications/DeepSeek Harness.app` 读取。用 `MOOS_ELECTRON_DSH_APP` 可指定其他路径。构建会检查 DSH 和 Electron 版本。

在 Finder 打开命令输出的 `Moos.app`。默认数据目录为 `~/Library/Application Support/dev.moos.agent.electron`。它包含独立 DSH 数据和默认工作区。第一次运行从随包模板加载插件设置。验收可为 Moos 主程序设置绝对路径 `MOOS_ELECTRON_DATA`，使用全新临时目录。

```sh
npm run test:electron
```

开发版通过本机回环提供工作台。Host 和插件安装器使用应用包内的 Moos 可执行文件，不需要另外安装 DSH、Node.js 或 pnpm。应用包使用本机临时签名，面向其他用户的分发和签名另行验收。

Moos 启动时在现有配置之后应用随包的 `execution.patch.yml`。它停用原版内置模型适配器、工具执行器和定时任务，清空四个内置预设的工具配置。会话仍使用原版的创建、恢复和显示协议。皮肤和普通界面插件仍通过原版宿主加载。其他执行类插件需要在 PI 接入后单独验收。

从工作台左下角进入原版「设置 → 模型」，或用 macOS 菜单「Moos → 模型服务…」打开该页。在原版提供商卡填写 Provider ID、API 地址、协议和 API 密钥，再从中转获取模型列表并勾选需要的模型，也可以手动添加模型 ID。展开各模型的高级选项可分别设置默认推理强度。保存前可选择其中一个模型测试连接。保存后，点击会话输入区的当前模型，再点弹出菜单中的「模型」切换。已配置推理强度的模型可在同一菜单中更改当前会话的推理等级。选用「Moos PI · 自动选择」时，已有 GLM 配置优先，否则使用首个已配置模型。外部服务地址须使用 HTTPS。

默认启动的 Moos 已内置 PI SDK，由本机 Host 与 Moos 调度器执行普通文本会话。服务及模型信息存于数据目录的 `providers.json`。同一服务的模型共用一条密钥记录，保存在本机 `private/credentials.json`，目录权限 0700，文件权限 0600。更改服务地址时需重新填写密钥。已有单模型配置可直接编辑并添加更多模型。

自动模式每个任务最多切换一次。首选模型在回复或调用工具前遇到额度、限流或连接错误时，切换至已配置的备用模型。常规验证命令在两轮文件修复后仍返回相同失败时，优先使用配置为 High 或 XHigh 的 OpenAI 中转模型接手，同一 PI 会话保留此前的工具结果。切换原因记录在「执行过程」。手动选定模型时按该模型运行。

「设置 → Token 用量」使用原版用量明细，汇总本机 PI 请求的服务返回值。会话输入框下方显示当前会话最近一次有记录请求的缓存命中率，以及该请求的输入 Token 和当时配置的上下文窗口。输入框中缺失的窗口或缓存信息显示为「—」。

会话中的「执行过程」可展开查看 PI 实际执行的动作和状态。正文保留回复与改动摘要，省略代码块和工具原始输出。Git 工作区在任务前后核对 Git 可见文件的新增、修改和删除，能识别命令产生的变化。没有可用 Git 快照时，文件清单显示已成功的 PI 写入与编辑操作。

会话最近一次 PI 任务失败、停止或中断后，输入框上方会显示「继续上次任务」。重新打开原会话也能继续。点击后按当前模型和权限提交一轮 PI 任务，使用该会话已保存的工具结果，原任务记录仍保留。

macOS 的受限命令可使用本机配套的 Node/npm 和 Git。保留已有 PATH，缺少 Node 和 npm 时查找常见 Homebrew 或 nvm 安装位置。Git 使用 PATH 上的 Homebrew Git，或直接调用 Apple 当前开发工具中的 Git。工具运行文件只读，命令仍受工作区和网络权限限制。

回复下方的「在新对话中分支」从选中的轮次继续。新会话有独立的 PI 历史，与原会话使用同一个工作区。选中的轮次有 PI 检查点时，分支继承该位置的工具结果。旧记录按已有对话文字恢复。

默认安装的用户扩展只有皮肤中心。构建会裁剪上游可选扩展、原执行器和附属的 Office、语音运行时。工作台保留项目、会话、文件树和插件安装器。需要扩展时，在侧栏「插件 → 添加插件」输入受信任的包名、GitHub 地址或本地路径。公开源安装已验证「自定义插件索引」，其他扩展的兼容性按插件验证。

侧栏「后台任务」显示当前所有工作区正在执行和排队的 PI 任务。点击条目回到对应会话，可用输入框旁的停止按钮结束该轮。添加工作区会在应用内打开目录选择器。

用以下方式启动内置 PI 调度验收。构建命令会输出验收版 `Moos.app` 的路径。运行命令中的路径替换为该应用包里的可执行文件。

```sh
MOOS_ELECTRON_INCLUDE_PI_FIXTURE=1 npm run build:app
MOOS_ELECTRON_PI_FIXTURE=1 MOOS_ELECTRON_DATA="$(mktemp -d)" "/path/to/Moos.app/Contents/MacOS/Moos"
```

验收模式默认选中「Moos PI · 本地调度验收」。可在默认工作区发送 `MOOS_FIXTURE_WRITE sample`，检查 `result.txt` 和对话中的工具结果。该模式只接受专用数据目录 `workspace` 下的项目和固定验收指令。PI 复用现有 Host 进程、SQLite 和 Moos 调度器。

PI 读取会话当前的「仅可查看」「工作区内修改」「完全权限」。在临时项目中发送 `MOOS_FIXTURE_POLICY` 可检查项目内写入及 Bash 越界行为。发送 `MOOS_FIXTURE_APPROVAL` 可在受限模式下测试一次性命令审批。受限命令由 macOS 沙箱执行，搜索通过受限 Bash 调用系统工具。

## 更新与用户数据保留

修改后默认只交付源码和验证结果，不自动替换或重启正式安装；只有用户明确要求部署时才更新应用包。更新继续使用 `dev.moos.agent.electron` 数据目录，不换一个空目录冒充历史恢复成功。

既有工作台配置不会被随包模板覆盖。聊天历史、PI 会话、模型服务及 `private/credentials.json`、皮肤、插件设置和工作区文件须保留。内置壳的离线升级仍可能更新其自身依赖元数据，不等于允许重置用户设置或卸载用户插件。若工作台配置缺失但发现旧数据，应用停止初始化并显示恢复提示，不自动创建一套新配置。恢复操作应先备份，再经用户明确同意处理，不应通过删除数据目录绕过提示。

隔离回归：`node --test apps/electron/profile-home.test.mjs apps/electron/profile-history.test.mjs`。覆盖初始化不覆盖既有文件、异常目录拒绝重建及 SQLite 消息/过程/设置重启读回；不替代随包插件升级、整应用 GUI 或正式安装更新验收。

内置壳升级前验证随包与已安装的包名、版本及升级包。版本相同不运行安装器；已安装元数据缺失或损坏时提示恢复，不静默补装；拒绝意外降级，安装器失败或未实际更新到目标版本时停止启动。错误提示不包含安装器原始输出。

升级边界回归：`node --test apps/electron/shell-update.test.mjs`。测试通过独立安装器子进程校验参数、同版跳过、异常拒绝，以及合成聊天/配置逐字节保持。它不是实际 DSH 插件安装器；现有真实安装器在失败前是否写入依赖文件及如何恢复尚未验收，本轮没有实现或宣称自动回滚用户配置。正式更新前须补齐真实安装器与隔离旧数据升级验证。

### 隔离包升级与界面恢复验收

将 `MOOS_ELECTRON_TEST_DSH_CLI` 指向当前隔离构建的 `Contents/Resources/host-runtime/bin/dsh` 后，运行 `node --test apps/electron/upgrade-integration.test.mjs`。此项使用真实随包安装器，准备合成旧壳及用户插件（准备阶段可能下载依赖），实际升级使用离线命令；只操作自动创建的临时数据。

显式 GUI 验收：`node scripts/verify-electron-recovery.mjs <仓库.generated/moos-electron下的Moos.app> <仓库artifacts下的输出父目录> [隔离皮肤夹具目录]`。拒绝正式安装路径；复制 QA 包并仅抑制 show() 后重签，使用 CDP 在后台窗口输入固定本地模型任务，正常退出重开并选择原会话，核对模型/合成密钥原字节、旧壳启动升级、两轮过程归属和可选皮肤；截图只存 artifacts。不能将后台窗口 DOM 检查称为正式窗口目视验收。E82 中继承分支的过程卡片缺失仍未解决，真实安装器失败回滚与完整 Swift 探针也不在通过范围。

E83 分支过程修复：Host 从实际继承前缀的消息 ID 与轮次边界查找原 PI 成功任务，并核对规范化工作目录，仅新增展示引用，不复制任务、消息、工具事件或用量，不执行父任务。普通 DSH 分支不一定带 parentSession，因此不依赖该字段；有父标识时进一步核验对应轮次。最多检查继承末尾 1600 条事件，未知或不完整来源不伪造卡片。已在隔离 Electron 验证单轮分支、排除后续轮次及刷新恢复；分支整应用重启及超限前缀仍需另验。E82 中过程卡片缺失属于修复前证据，保持原记录。
